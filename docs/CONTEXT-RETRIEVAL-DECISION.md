# Decision memo: pinned repository context for guides

2026-09-26 · Revised after discussion: local search experiment · Code examined: `2b678af`

**Recommendation:** compare the existing fixed selector with model-directed local text search over pinned Git source. Give the model two bounded tools: `search` and `read_lines`. Start without language-specific parsers, embeddings, a persistent index, or a remote retrieval service. Preserve source provenance, privacy filtering, explicit consent, and raw inventory; deliberately replace the single provider call with a bounded tool loop for the experiment. See the [implementation plan](../tasks/context-retrieval-plan.md).

Implementation follow-up: the user subsequently authorized the interactive search loop using the existing OpenAI client. See [execution tasks](../tasks/search-agent-implementation.md) and [current reference](REFERENCE.md). The baseline trace below records the original design; it is not the current consent UI or request count. The implemented path preserves original session source evidence and stores submitted tool excerpts plus retrieval scope in the derived guide bundle. Empirical guide quality and live-provider latency remain unmeasured.

## Baseline path, traced before implementation

Read [REFERENCE.md](REFERENCE.md) and [CONSTRAINTS.md](../CONSTRAINTS.md). `docs/ARCHITECTURE.md` is absent from this checkout and tracked-file inventory; the following trace comes from implementation. The contract also mentions `internal/analysis`, which is absent here.

1. **Pin source.** [`source.PinWithTiming`](../internal/source/git.go) reads GitHub metadata, opens a private bare Git view borrowing only local object data, and verifies one merge base ancestral to both pinned tips. Missing objects may trigger a bounded exact-tip fetch into temporary storage and a metadata recheck. Reviewed hooks, filters, configuration, replacement refs, and working files are not source inputs. [`inventory.Build`](../internal/inventory/inventory.go) compares merge base to head, constructs actual blob-to-blob patches and immutable units, and records unavailable content explicitly.
2. **Select evidence before consent.** [`review.OpenWithConfig`](../internal/review/review.go) calls [`context.Retrieve`](../internal/context/retrieval.go) while that Git view is open. It lists merge-base and head trees; merge-base evidence is considered only for deleted paths, with other context from head. Ranking is exactly: same-directory manifest/doc/test = 0; same-directory source or other-directory manifest/doc/test = 1; other source = 2. Ties retain tree order. There is no identifier, import, dependency, or semantic search. `TextReference` exists but is not emitted. Changed files can themselves be evidence; “unchanged context” in the prompt is not a checked invariant.
3. **Bound and filter retrieval.** Defaults are 100 retained files, 32 KiB per blob read, 256 KiB retained evidence, five seconds. `View.Blob` fails oversized reads without partial output: the 32 KiB setting is effectively a whole-file eligibility cap, not a window around relevant lines. Accepted evidence starts at line 1; only the aggregate remaining-byte budget truncates it. Path policy precedes reading, complete accepted blobs are checked for binary/credential-like content before excerpting, and symlink/submodule evidence is skipped. Evidence carries repository, commit, blob, byte-preserved path, line range, reason, and ID. Omissions are local. The temporary view is then closed; snapshots retain patches and bounded evidence, not arbitrary unchanged source.
4. **Consent is general, not package inspection.** `g` opens [`guideConsentView`](../internal/tui/guide_consent.go); Enter invokes [`requestGuide`](../cmd/pr-review/wiring.go), which rejects offline access before constructing a credential-bearing analyzer. The endpoint shown is captured for that UI lifecycle. PR-list cache reuse makes no provider call. The [`e` view](../internal/tui/render.go) lists evidence paths, ranges, reasons, and omissions, but does **not** display excerpt bodies or allow exclusions. `privacy.Policy.Excluded` is a library facility; the CLI exposes no exclusion flags and current guide generation passes an empty policy. Raw diffs remain locally inspectable.
5. **Assemble upload.** [`DeriveGuide`](../internal/review/review.go) uses only saved inventory/context. [`guide.InputFrom`](../internal/guide/input.go) reapplies privacy, propagates exclusions across file units and rename aliases, and gives patches priority over evidence within 400 units, 32 KiB/unit, and 512 KiB total content. It preserves recognized privacy omissions from retrieval. Credential detection remains heuristic; oversized/unexamined blobs do not receive a complete content scan. Excluding a path is not a guarantee that another allowed file never mentions that path or its content.
6. **Request and result.** [`guide.OpenAI`](../internal/guide/openai.go) sends one non-streaming HTTPS `POST /v1/responses`, `store:false`, strict `pr_review_guides` schema; request/response envelopes are capped at 2/4 MiB and analysis at 60 seconds. The normal client rejects redirects. The prompt contains units and evidence excerpts, plus changed-unit withholding counts/generic reasons; it does not serialize the evidence omission ledger, or all provenance fields. Successful output is validated/reconciled, with uncovered units synthesized into an ungrouped guide. Completed attempts create a derived session with empty progress; cancellation preserves the original. Valid generated bundles are cached locally; cache validation also checks inventory identity and prompt version, beyond the public repository/PR/base/head key. Neither that cache nor old snapshots should silently acquire new retrieval semantics.

`store:false` is not a zero-retention guarantee. OpenAI distinguishes application state from abuse-monitoring logs, which may retain content by default; configured alternative endpoints have their own policies. The inline code comment claiming “no server-side retention” is too broad. [Official data controls](https://developers.openai.com/api/docs/guides/your-data).

## Options and tradeoffs

These quality and performance assessments are hypotheses; no retrieval or generation benchmark was performed in this exploration.

| Approach | Guide quality | Latency and update cost | Storage and privacy |
| --- | --- | --- | --- |
| Current fixed ranking | Predictable broad orientation; misses distant definitions and large files, and unrelated docs can consume budget | No build; tree listing, sorting, and individual blob reads recur on fresh comparisons | Only bounded saved evidence; one bounded upload after consent |
| Local lexical + syntax index | Exact definitions/import targets, test references, and doc names can explain cross-file behavior; weak on synonyms, dynamic dispatch, and unsupported languages | Cold work scans bounded eligible blobs; warm lookup avoids rereads; only new blob/parser combinations need parsing, though tree membership still costs work | Local postings, metadata, and retained chunks enlarge sensitive storage; no indexing upload; exact selected package can be inspected |
| Model-directed local lookup tools | Adaptive multi-hop discovery could resolve ambiguity; can also chase noise or obey source prompt injection | Extra model round trips and tokens; local searches still need an index or repeated scans | Results progressively leave the machine; per-result consent or preapproved corpus required; conflicts with today's one-call contract |
| Remote embeddings + vector search | Potential conceptual/synonym recall; similarity does not establish a definition, dependency, or correct revision | Cold chunking/embedding/upload, incremental re-embedding, query-network and generation latency; shared infrastructure can amortize costs | Remote derived data, access control, deletion and credentials; remotely computing embeddings exposes source before final guide consent |

The selected experiment exposes `search(pattern, path_glob, revision)` and `read_lines(path, start, end, revision)` over an approved pinned corpus. These are language-independent text operations, not a shell or working-tree reader. The model follows names and imports itself. A parser or index can be added later if measured ambiguity or scanning cost warrants it. OpenAI's documented function-calling flow returns application-executed tool results in subsequent requests, requiring a deliberate change to the present request contract. [Function calling](https://developers.openai.com/api/docs/guides/function-calling).

Local execution does not mean local-only disclosure: tool results are uploaded when returned to the model. The experiment therefore previews a filtered, bounded set of pinned files and obtains approval for incremental disclosure from that set before the first request. Users can inspect full eligible text and exclude files; excluded files never become search candidates. A local ledger shows what actually left the machine. Per-result approval is deferred to avoid interrupting every lookup.

## What the external evidence supports

Cursor's January 2026 engineering post describes Merkle-tree change detection, syntactic chunks, cached embeddings keyed by chunk content, and reuse of teammates' indexes with content-proof filtering. It explicitly describes initial file uploads. Its reported onboarding gains concern Cursor's infrastructure, not this CLI or PR guide quality. Git already supplies immutable content identities here; copying Cursor's workspace synchronization system is unnecessary. [Cursor engineering](https://cursor.com/blog/secure-codebase-indexing).

Turbopuffer's current vendor account confirms Cursor uses its vector search and reports a 95% cost reduction when migrating from a prior provider; it says plaintext code is not stored in Turbopuffer. That is a vendor claim about storage, not absence of uploads or a local-index cost comparison. Its documented architecture uses object storage with SSD/memory caching and supports vector and BM25 search. This does not by itself supply chunking, embedding generation, pin validation, or upload consent. [Vendor account](https://turbopuffer.com/blog/turbopuffer), [database concepts](https://turbopuffer.com/docs/concepts).

Older search-indexed Cursor security text describes obfuscated paths and particular sync intervals, but the current [security page](https://cursor.com/security) no longer establishes those details; do not promise them here. Current ignore documentation explicitly notes terminal/MCP access limitations. Exclusion controls need enforcement at every outbound path, not merely an indexing ignore file. [Cursor ignore documentation](https://prod.cursor.com/docs/reference/ignore-file).

## Decision gate

Compare A, the existing fixed selector and single call, with B, a diff-first guide request using bounded search/read tools. Use synthetic histories across languages, equal unique-source upload limits, the same model and final guide rubric, and explicit measurements of extra request rounds, replayed bytes, latency, and tokens. Keep the final guide schema and coverage validation. Do not claim an equal-compute comparison: adaptive lookup spends additional inference.

Reopen only the saved exact pins through an isolated local object view for the experiment; never follow current branches or automatically fetch replacements. If those objects are unavailable, offer the existing saved-evidence path with an explicit limitation. No persistent index or full-source retention is needed. The plan specifies source lifetime, consent, failure behavior and success gates. Add indexing only if repeated scans are the demonstrated bottleneck; add parsers only if search ambiguity materially harms guides.
